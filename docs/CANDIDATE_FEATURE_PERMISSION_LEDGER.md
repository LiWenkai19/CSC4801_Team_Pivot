## CAN-001：候选人简历读取与修改

### 用户已确认的规则

1. 候选人只能读取自己的简历，不能读取其他候选人的简历。
2. 已登录雇主只能查看申请过自己职位的候选人的简历。
3. 只有候选人本人能够修改自己的简历，雇主及其他候选人均无修改权限。
4. 权限由后端校验，不能只依赖前端隐藏按钮。

### 权限矩阵

以下成功状态以目标资料存在、请求合法为前提。

| 访问身份与关系 | 读取简历 | 修改简历 |
| --- | --- | --- |
| 候选人本人 | 允许，200 | 允许，200 |
| 其他候选人 | 拒绝，403 | 拒绝，403 |
| 候选人申请过其职位的已登录雇主 | 允许，200 | 拒绝，403 |
| 没有对应投递关系的已登录雇主 | 拒绝，403 | 拒绝，403 |
| 未登录、令牌无效或过期、令牌对应账号不存在 | 拒绝，401 | 拒绝，401 |

雇主读取判定：存在至少一条该候选人的 Application，且关联 Job 的 employer_id 等于当前登录雇主 ID。候选人申请了雇主 A 的职位，不会因此向雇主 B 开放简历。即使知道候选人的 ID，也必须满足同样的服务端授权条件。

### 已完成的行为与数据边界

- 当前简历为纯文本 `resume_text`，支持本人读取、局部更新和清空。
- 修改时省略简历字段保留原值，传空字符串清空；显式传入 `null` 或非字符串返回 422。
- 保留中文、换行和首尾空白；候选人页面按文本展示并转义 HTML。
- 返回资料字段限定为 `user_id`、`display_name`、`resume_text`、`skills`，不返回邮箱、密码哈希或认证令牌。因此当前雇主读取接口也会返回显示名称和技能。
- 更新请求不能伪造 `user_id`、`candidate_id`、`role` 等归属或身份字段，额外字段返回 422；本人身份来自认证账号。
- 首次填写资料使用单独的创建接口，归属绑定本人；重复创建返回 409，不能借此覆盖已有简历。
- 候选人读取其他人的 ID 先被拒绝为 403；通过读取角色与本人范围检查后，目标账号或资料不存在、目标不是候选人时返回 404。UUID 格式错误返回 422。

### 当前实现的边界，后续需求变化时复核

以下是当前代码行为，不代表用户已经单独确认每一项业务政策。

| 边界 | 当前行为 |
| --- | --- |
| 申请状态变化 | Pending、Interviewing、Rejected、Accepted 均构成投递关系，不随状态变化撤销读取权限 |
| 职位软删除 | 保留历史申请关系，因此所属雇主仍可读取 |
| 对应申请记录移除 | 若不存在该候选人对该雇主其他职位的申请，雇主失去读取权限 |
| 职位归属变化 | 以数据库中职位当前的 employer_id 为准，每次请求重新判断 |
| 多个职位、多次对应申请 | 只要至少一个职位满足关系即允许读取，不要求申请某个指定职位 |
| 简历更新后的雇主读取 | 返回当前保存的简历，无投递时的历史快照 |
| 并发保存 | 没有版本号或冲突检测，同一字段以后提交的值为准 |
| 简历长度 | 当前没有额外的业务长度上限 |

PDF/Word 文件上传、解析、下载，以及简历历史版本未在本项中实现。

## CAN-002：防止重复申请同一职位

### 用户已确认的规则

候选人申请过一个职位后，不允许重复申请同一职位；重复操作必须有提示反馈。重复以“同一候选人 ID + 同一职位 ID”判断，不按职位标题或公司名称判断。

### 已有实现与本轮补充

- `POST /candidate/jobs/{job_id}/applications` 要求已登录候选人，candidate_id 来自当前账号，不能替他人申请；资料未完成返回 404，匿名请求返回 401，雇主请求返回 403。
- 首次申请成功返回 201，初始状态为 Pending。服务层先查同一 candidate_id、job_id 的记录，存在则返回 `409`，响应为 `{"detail":"Already applied"}`，不新增记录或覆盖原申请。
- Application 模型、独立迁移及六表模型已有联合唯一约束 `uq_application_candidate_job`。数据库冲突时回滚；确认存在对应申请后转换为相同的 409 提示。没有新增表或修改迁移。
- 列表与详情返回当前候选人的 `applied` 标记；申请按钮在提交中禁用，显示“提交中…”，已申请则禁用并显示“已申请”。刷新页面后重新从后端获取该标记。
- 原页面会直接显示英文冲突消息，并在刷新中卸载提示。本轮新增 `ApplicationFeedback.tsx`：重复返回时显示“你已申请该职位，请勿重复申请。”，刷新完成后已申请状态也持续显示同样的中文说明。

### 权限与边界

| 场景 | 当前行为 |
| --- | --- |
| 同一候选人重复申请同一有效职位 | 409，提示已申请，保留原记录 |
| 同一候选人申请另一个职位 | 允许，前提是职位有效且资料完整 |
| 不同候选人申请同一职位 | 分别允许，不共享已申请状态 |
| 原申请为 Pending、Interviewing、Rejected 或 Accepted | 均视为已申请，不能重新申请；查重不按状态过滤 |
| 同名职位但职位 ID 不同 | 视为不同职位 |
| 职位不存在或已软删除 | 先返回 404，不进入重复校验 |
| 多标签页、重试或直接调用 API | 后端仍查重，数据库唯一约束兜底；真实 PostgreSQL 并发待最终验收 |
| 客户端伪造 candidate_id、申请状态等字段 | 请求只接受空对象，额外字段返回 422 |
| 网络中断后不确定是否成功 | 重试时后端重新判断；若之前已成功，返回 409 并同步已申请标记 |
| 物理删除原申请记录 | 当前查重依据不再存在，可能重新申请；删除及撤回机制未在本项中新增或授权 |

状态变化仍禁止重复申请符合本项“不允许重复申请”的规则；若后续增加撤回、重新申请或职位归档政策，应重新核对本条目。

## CAN-003：双方查看申请状态与面试邀约

### 用户已确认的规则与流程

候选人和雇主均可查看当前申请状态与面试邀约情况。用户确认沿用现有流程：申请进入 Interviewing（面试中）代表收到面试邀约，候选人选择时段后，双方查看预约结果；不新增独立邀约记录。

本项是读取功能。发送邀约、雇主修改申请状态、管理时段等写入功能不因本项而自动新增或授权；由后续需求或对应模块接入完成。

### 已有功能

- 候选人“我的申请”展示职位、公司、当前申请状态及已有面试预约；Interviewing 且尚未预约时提供选择时段入口。
- 候选人列表与详情、雇主职位申请列表复用 `application_public` 组装数据，读取同一条 Application 和关联 Booking，避免双方维护不同状态副本。
- 状态原值为 Pending、Interviewing、Rejected、Accepted；候选人页面对应“待处理、面试中、已拒绝、已录用”。
- 有预约时返回 booking ID、slot ID、开始时间、结束时间；无预约时 `booking=null`。接口时间统一为 UTC，候选人页面按 Asia/Shanghai（UTC+8）展示。

### 读取权限

| 身份 | 可读取范围 | 范围外的处理 |
| --- | --- | --- |
| 已登录候选人 | 本人的申请列表、单条申请状态和预约结果 | 他人申请详情返回 403 |
| 已登录雇主 | 自己职位下的申请状态、候选人标识及预约结果 | 其他雇主的职位申请列表返回 403 |
| 候选人调用雇主接口或雇主调用候选人接口 | 不允许跨角色使用 | 403 |
| 未登录、无效/过期令牌或账号不存在 | 不允许读取 | 401 |

候选人列表直接按当前登录用户 ID 过滤；详情核对 Application.candidate_id。雇主接口先核对 Job.employer_id，不因同公司、知道职位 ID 或该候选人投递过自己的另一个职位而开放其他职位记录。

### 邀约与预约的展示含义

| 当前数据 | 当前可判断的信息 |
| --- | --- |
| Interviewing 且 booking=null | 已进入邀约流程，待候选人选择时段；尚无已确认时间 |
| 存在 booking | 已保存预约，可查看起止时间；申请状态独立展示 |
| 非 Interviewing 且 booking=null | 当前不处于可选时段的邀约状态；不能据此推断历史上是否发过邀约 |
| 非 Interviewing 但仍存在 booking | 保留并展示已有预约，不因状态改变自动取消 |

没有可用时段时显示暂无时段，不代表没有邀约。预约时间已过去不会自动变成“面试已完成”，当前没有面试完成、取消、改期或独立邀约历史字段，也没有地点或会议链接。

### 接口与接入位置

| 用途 | 现有接口 |
| --- | --- |
| 候选人查看本人全部申请 | `GET /candidate/applications` |
| 候选人查看本人单条申请 | `GET /candidate/applications/{application_id}` |
| 雇主查看自己职位下全部申请 | `GET /employer/jobs/{job_id}/applications` |

- [服务层](../backend/app/candidate/service.py)：`owned_application`、`application_public`、`employer_applicants`。
- [路由与权限依赖](../backend/app/candidate/router.py)；[申请及预约响应结构](../backend/app/candidate/schema.py)。
- [候选人申请页面](../frontend/candidate/src/pages/candidate/ApplicationsPage.tsx)。雇主接口的每行包含申请 ID、候选人 ID、显示名称、技能、匹配分数、职位、公司、status 和 booking；不包含简历或认证机密。
- 雇主页面所有者可直接消费现有职位申请列表接口，按上表显示状态与邀约/预约情况，统一时区，并处理无申请和无预约的情况。当前未新增雇主界面，也未修改团队入口。

### 当前边界与验收安排

- 无申请时列表返回空数组；申请/职位不存在返回 404，路径 UUID 格式错误返回 422。候选人的详情接口先查询记录，记录存在但不属于本人时返回 403。
- 职位软删除后仍能查看历史申请和预约，不能因此自动隐藏或清空相关记录。
- 每次请求读取数据库当前状态；候选人页面在进入页面、重新加载或预约成功后重新获取。当前无跨客户端实时推送或自动轮询，停留页面不会自动显示另一端刚刚发生的变更。
- 当前不保存独立邀约历史，不能从“当前非面试中”推断“从未邀约”；状态离开 Interviewing 后已有预约仍保留，应同时展示二者。
- 外键关联的职位、公司资料和预约时段由对应模块提供；历史记录物理删除、数据异常修复及统一撤销机制不在本项中新增。
- 本轮检查现有实现与原需求，未重复搭建接口、修改业务代码、新增或运行测试。已有测试涉及本人列表、跨账户访问、雇主职位归属及预约读取；最终样例仍按用户安排在开发完成后统一制作与执行。
- 后续重点验收四种状态、邀约未预约、无可用时段、预约后双方信息一致、跨候选人/跨雇主越权、状态改变后预约保留、历史职位、UTC/本地时间展示及刷新后的最新数据。

## CAN-004：所有业务查询接口必须校验权限

### 用户已确认的规则

用户请求业务查询时，后端必须审核当前角色是否有权执行该查询。用户明确范围为所有业务查询接口；不仅检查是否登录，还需核对所请求操作及目标数据是否在该账号权限范围内。

本条是 CAN-001～003 及后续功能共同遵守的查询授权要求，不扩大候选人或雇主原有的数据访问范围。

### 当前授权链路

1. 后端验证访问令牌的签名与有效期，查找其对应的当前数据库账号；无有效身份返回 401。
2. 使用数据库账号的 role 判定角色，不接受请求正文、查询参数或前端页面声明的角色作为授权依据。
3. 对指定角色的接口使用 `require_candidate` 或 `require_employer`；共享接口按本人的身份或具体投递关系判定。
4. 列表查询限定允许的数据范围；单条记录核对本人归属或职位所属雇主。角色不匹配或已有记录不在授权范围时返回 403，目标不存在按相应接口返回 404。
5. 仅返回接口明确允许的业务字段，不返回密码哈希、令牌或其他账号的认证信息。

认证及权限判断本身可能需要读取账号、投递记录或职位归属；“先授权”指完成必要判断后才提供受保护业务结果，不要求在验证身份之前完全禁止所有内部数据库读取。数据库 Session 的创建本身也不等于授予查询权限。

### 当前业务读取接口清单

已根据 `app.candidate_main:app` 挂载的路由逐项检查；共 8 个业务 GET 接口。

| 接口 | 允许角色 | 数据范围或附加条件 | 当前校验位置 |
| --- | --- | --- | --- |
| `GET /users/me` | 已登录候选人、雇主 | 当前账号及其对应角色的资料完成状态 | `get_current_user`、`public_user` |
| `GET /users/candidates/{candidate_id}/profile` | 候选人、雇主 | 候选人仅本人；雇主仅申请过自己职位的候选人 | `get_current_user`、`readable_profile` |
| `GET /candidate/jobs` | 候选人 | 资料完整；全部未软删除职位，匹配与已申请标记属于当前候选人 | `require_candidate`、`owned_profile`、`list_jobs` |
| `GET /candidate/jobs/{job_id}` | 候选人 | 本人资料完整，目标职位有效；不返回其他候选人申请信息 | `require_candidate`、`owned_profile`、`active_job` |
| `GET /candidate/applications` | 候选人 | 仅 Application.candidate_id 等于当前账号 ID 的记录 | `require_candidate`、列表 where 条件 |
| `GET /candidate/applications/{application_id}` | 候选人 | 该申请属于本人 | `require_candidate`、`owned_application` |
| `GET /candidate/applications/{application_id}/slots` | 候选人 | 本人申请、Interviewing、尚未预约；只查对应雇主未来空闲的有效时段 | `require_candidate`、`eligible_application`、`available_slots` |
| `GET /employer/jobs/{job_id}/applications` | 雇主 | 职位必须属于当前雇主；只查此职位的申请及关联预约 | `require_employer`、`employer_applicants` |

空列表只表示授权范围内没有记录，不能通过移除过滤条件返回全表。本人申请列表不要求先完成资料；无申请时返回空列表。时段查询的业务资格不满足可能返回 409，不应将其误写为认证失败。

### 范围与接入边界

- 注册、登录和换取令牌是用于建立身份的公开认证入口，不强制先登录；其中的受控账号查询不等于开放任意业务数据查询。API 文档等框架路由不作为业务数据库查询接口。
- 当前没有对用户开放任意 SQL、表名、字段名或全库浏览接口；不因“请求查询数据库”新增此类入口。
- 当前是应用层授权，并非数据库账号级的行级安全策略。持有数据库凭据直接连接、维护脚本、迁移与种子数据脚本不在 HTTP 用户查询授权范围内，不能据此声称已被同一权限链路保护。
- 本次也检查了团队原应用的 `/users/me`，它使用 `get_current_user` 限定本人；团队原应用尚未挂载完整候选人扩展，不将其他队友未来接口视为已完成审计。
- 后续新增业务查询入口必须补充对应角色、对象归属、列表过滤及返回字段规则；不能仅复用 `get_db` 或仅隐藏前端入口。内部 service 函数不能默认当作独立公开接口调用，公开入口必须保留完整授权链路。
- 若后续增加 AI/Agent 数据查询，也需要单独登记入口及可信身份传递方式；本项不声称已经实现或审核尚不存在的工具链路。

## CAN-005：技能标签搜索与自定义

### 用户已确认的需求

雇主为职位添加所需技能、候选人填写简历资料时选择自身技能，均使用标签形式。用户在搜索框输入文字，下拉框推荐匹配技能，例如 `j` 推荐 Java、JavaScript；点击即选为标签。找不到所需技能时可通过自定义选项创建标签。

### 本轮实现

- 新增共享 `SkillTagPicker`、局部样式及 `skillCatalog` 预置目录，支持点击选择、移除标签、方向键导航、Enter 选择、Escape 关闭、中文输入法及可访问状态提示。
- 搜索忽略大小写，前缀优先，其余包含匹配随后，最多显示 8 个预置建议；已选技能从建议中排除，不允许同名重复选择。
- 非空输入没有同名目录项且未选中时，可创建自定义标签；即使有部分匹配结果也保留自定义选项。空白不可创建，C++、C#、Node.js 等标点保留。
- 候选人首次填写和编辑资料共用的 CandidateForm 已接入。标签以规范化字符串数组提交到原接口，保存失败保留选择，提交中禁用；未知的历史技能继续回显。
- 仅输入、没有选择或创建的文字不会被当作标签；标准表单提交会提示先完成选择或清空搜索框，防止漏存。
- 另提供无数据库的组件预览页，包含候选人完整表单与雇主独立组件用法；该预览不代替正式雇主职位页面。

### 权限、存储与当前边界

| 场景 | 当前规则 |
| --- | --- |
| 搜索推荐 | 本地共享初始目录，不查数据库，不读取他人简历、技能或职位草稿 |
| 候选人保存技能 | 原接口仅本人可创建/修改，写入 CandidateSkill |
| 雇主保存职位技能 | 组件可复用；正式保存由雇主模块接入，必须校验雇主身份和职位归属后写入 JobSkill |
| 自定义标签 | 先保留在当前表单，保存后随当前资料/职位持久化；不会自动发布到公共推荐目录 |
| 匹配规则 | 保持 trim、lower、去空和去重；Java 与 JavaScript 不合并，不增加模糊评分或同义词替换 |
| 简历形式 | 仍为现有文本简历，本项不新增 PDF/Word 上传或技能自动提取 |
| 目录和限制 | 预置目录可扩展，尚无全库热门统计；本轮未新增业务长度、数量或行业分类限制 |

“自定义不自动加入公共目录”是本轮实现边界；如后续需要共享词库，应单独确定发布、去重、审核及查询权限规则。

## CAN-006：职位推荐列表与评分占位

### 用户已确认的需求

候选人上传简历后可以获得职位推荐列表，按候选人与各职位的匹配分数降序排列。评分算法先用占位符，后续再开发。本项明确替代此前运行服务中按技能交集计算真实分数的行为。

### 本轮实现与入口

- 复用 `GET /candidate/jobs`、`GET /candidate/jobs/{job_id}`，保留全部未软删除职位、职位详情、技能与本人已申请标记。
- 新增 [占位评分模块](../backend/app/candidate/recommendation_scoring.py)：`match_score(candidate, required)` 保留双方技能输入接口，目前统一返回 0；没有生成随机或伪造的不同匹配分数。0 代表算法未开发，不代表不匹配。
- 服务端继续按 `(-score, title.lower(), id)` 排序。当前全部为同分，因此按职位名称（忽略大小写），再按职位 ID 稳定排序；真实算法替换后可直接产生分数降序结果。
- 职位列表、详情及雇主职位申请行均使用同一占位函数，返回 `score_kind="placeholder"`；前端列表/详情显示“0 分（占位）”，推荐页明确解释算法待开发。雇主接入页面也必须识别该标记，不能继续解释为真实百分比。
- 候选人首次资料保存并确认成功后进入 `/candidate/jobs`；已有资料编辑页提供“查看职位推荐”入口。请求失败不进入成功流程，原表单的保存失败处理保持适用。
- [列表及详情评分接入](../backend/app/candidate/service.py)、[响应 schema](../backend/app/candidate/schema.py)、[前端分数展示](../frontend/candidate/src/components/candidate/RecommendationScore.tsx)。

### 权限与边界

| 场景 | 当前行为 |
| --- | --- |
| 未登录或令牌失效 | 401 |
| 雇主调用候选人推荐接口 | 403 |
| 候选人尚未创建资料 | 404，提示先完成资料 |
| 无有效职位 | 返回空列表，页面提示暂无可申请职位 |
| 职位软删除 | 不出现在推荐列表，直接访问详情返回 404 |
| 已申请职位 | 继续展示并标记已申请，不重复申请；没有因本项新增隐式过滤 |
| 修改简历或技能 | 下次请求读取最新本人资料，当前占位分数仍为 0；无评分缓存或数据库分数表 |
| 客户端指定候选人或分数 | 推荐以服务端登录身份、服务端评分为准，不采信客户端分数 |

当前“上传简历”沿用文本简历资料保存，不新增 PDF/Word 上传、解析或从简历提取技能。此前允许简历/技能稍后补充的规则保持适用：资料存在即可查看职位，本轮没有擅自增加“必须填非空简历”的门槛。列表目前展示全部有效职位，没有新增 Top-K、最低分阈值或分页规则。

### 后续算法与验收

- 后续在独立评分模块实现真实算法，再更新 `score_kind` 的后端/前端类型及说明；可继续复用排序和列表接口。原 `app.matching.match_score` 留存供历史参考，目前服务不调用，不表示它已被选作最终算法。
- 正式算法的输入、分数范围、空技能规则、简历使用方式及同义词策略等后续再确认，本轮不提前实现。
- 本轮按用户安排不新增或执行测试样例。旧 `test_jobs_all_active_order_and_live_scores`、雇主分数及集成测试仍断言此前的真实技能重合分数，统一验收时需按新阶段规则更新；先前套件通过结果不能当成本轮回归通过证据。
- 最终样例应覆盖资料保存后的入口、权限、空职位、隐藏职位、已申请标记、占位标记、同分稳定排序，并在真实算法开发后使用可控分数验证降序。
