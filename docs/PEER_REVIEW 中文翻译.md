# 跨团队同伴审计

在审查另一团队的项目之前，请先阅读本文档。只有在遵循本流程且不越出安全边界的前提下，一项发现才有资格得分。

> **必须**（MUST）与**不得**（MUST NOT）级别的需求计入评分。**应当**（SHOULD）级别的条目为建议项，除非被另一条**必须**级需求所要求，否则不计分。**可以**（MAY）级别的条目为可选项。

## 0. Safety boundary（安全边界）

仅审计目标团队在其 `main` 分支最新提交处的源代码，使用该仓库的 `Dockerfile` 构建，并在你自己的机器或你自己的 CI 中进行。修复会被推送到 `main`，因此审计须始终针对最新提交，而非旧提交。你**可以**：

- 阅读源代码与文档；
- 从仓库的 `Dockerfile` 构建环境，并从中运行项目写入文档的测试套件与本地服务器；
- 针对本地检出编写并运行一个最小回归测试；以及
- 对该检出运行静态分析、代码检查工具（linter）、依赖扫描器与机密扫描器。

你**不得**：

- 测试任何已部署的 URL、共享的预发布（staging）系统、真实第三方账户，或目标团队未明确提供为本地测试数据的任何资源；
- 实施负载测试、拒绝服务、资源耗尽、破坏性测试、社会工程或机密外泄；
- 修改目标团队的分支、拉取请求、CI、仓库设置，或除你所提交的那份发现之外的任何 issue；
- 公布机密值或个人数据；只报告其脱敏后的位置；以及
- 扫描本地检出之外的任何内容。

即使某种技术可能揭示有效缺陷，这些限制仍然适用。违反安全边界属于学术诚信问题，而不仅仅是一份无效报告。

## 1. Audit target（审计目标）

1. 克隆指定的仓库，并检出其 `main` 分支上的最新提交。
2. 从仓库的 `Dockerfile` 构建环境（参见 [`DOCKER.md`](DOCKER.md)）。你**不得**修改目标源码以使构建成功。
3. 按照目标团队的 `INSTALL.md` 启动、迁移、灌入种子数据、测试并对该环境做冒烟测试。你**不得**修改目标源码，也不得在分支或拉取请求上修复其安装配置。
4. 用检出的源码进行代码检视，用运行中的 Docker 环境进行运行时审查。
5. 在每份报告中记录你观察到该缺陷的确切提交 SHA。
6. 仅在公布的审计窗口内提交发现。

未写明观察到缺陷的确切提交 SHA 的发现是不可复现的，因而无效。如果仓库的 `Dockerfile` 无法构建或无法运行，请报告该环境问题（其本身就是一项有效发现），而不是修改目标源码。当目标团队将修复推送到 `main` 时，针对 `main` 上的最新提交重新测试。

## 2. Valid finding standard（有效发现标准）

有效发现（valid finding）**必须**满足以下每一项条件：

- **范围之内：** 它违反了课程 [`REQUIREMENTS.md`](REQUIREMENTS.md) 或目标团队精确的 `SPEC.md` 中的某条**必须**级需求，或违反了某项向用户暴露且已写入文档的行为。
- **确实存在：** 它出现在由目标仓库在 `main` 最新提交处的 `Dockerfile` 所构建的环境中，且未改动目标源码。
- **可复现：** 报告给出确切的安装与执行命令，以及观察到它所需的最小可行输入或测试。
- **可观察：** 期望结果与实际结果以具体方式存在差异。风格偏好、无可达路径的假想隐患，或缺乏支撑的扫描器告警，均不是缺陷。
- **独立：** 它不是已报告根因的重复症状。提交前请检索开放与已关闭的 issue。
- **安全：** 它是在第 0 节的边界之内发现的。

每一份发现都必须通过 [`templates/github/ISSUE_TEMPLATE/audit_bug_report.yml`](templates/github/ISSUE_TEMPLATE/audit_bug_report.yml) 处的 GitHub Issue Form 提交；每个团队都**必须**在自己的仓库中启用该表单。缺少必填字段或复现步骤会使报告无效。一个 issue **应当**描述一个根因；仅当发现互不相关时才拆分。

### Report types（报告类型）

每份报告**必须**使用 `audit:report` 与 `status:needs-triage`，外加恰好一个类型标签。恰好施加一个类型标签：

| Label | Use when |
|---|---|
| `type:functional` | 必需的工作流、规格规则或要求的测试/CI 行为缺失、不正确、崩溃或无法完成。 |
| `type:security` | 身份认证、授权、隐私、注入、XSS、提示词安全、机密处理或测试隔离被违反。 |
| `type:performance` | 写入文档的性能期望在一个小型、安全的测试夹具上未达成；负载或资源耗尽测试一律不被允许。 |

选择最能代表根因的类型。当多种类型都可能适用时，`type:security` 优先。

每个团队都从 [`templates/github/labels.yml`](templates/github/labels.yml) 将全部审计标签（`audit:*`、`type:*` 与 `status:*`）导入自己的仓库，以便每个仓库使用同一套标签。

## 3. Reproduction quality（复现质量）

不具备先前背景的读者应当能够复现该结果。请包含：

- 操作系统与 Docker 版本，以及你构建并观察到该缺陷的确切提交 SHA，外加任何与 `INSTALL.md` 的偏离；
- 确切的重置与种子数据命令；
- 确切的请求、UI 操作序列或最小失败测试；
- 相关的响应、异常、断言或数据库计数；
- 期望行为，并附需求 ID 或 `SPEC.md` 章节；以及
- 实际行为，并对机密与个人数据进行脱敏。

截图**可以**补充命令，但**不得**取代命令。对于并发发现，请使用同步屏障（synchronization barrier）或其他可重复的方法；顺序发出的请求不能证明并发缺陷。对于扫描器发现，请将告警追溯到可达的代码路径，并提供无害的本地证明。

## 4. Triage and resolution（分诊与解决）

每一份新报告都以分诊（triage）状态 `status:needs-triage` 开始。目标团队或教师将其更改为下列之一：

- `status:confirmed`：可复现、在范围之内、安全，且非重复；
- `status:rejected`：不满足第 2 节中的任一条件；
- `status:duplicate`：与更早的某个 issue 具有相同根因，该 issue **必须**被链接；或
- `status:fixed`：修复与回归证据在所链接的修复提交（fix commit）上通过。

报告者**不得**把自己的报告标为 confirmed 或 fixed。对于已确认的 issue，目标团队**必须**添加回归测试，通过其正常的审查流程修复该问题，并开启一个拉取请求，该请求须链回缺陷报告 issue，并记录根因、修复与验证。报告者**可以**从所链接的提交构建修复后的环境，在本地重新测试，并以结果留言。

所有报告与修复**必须**符合公布的截止时间。

如果团队意见不一致，各方**应当**发表一条简洁、以证据为依据的评论，并请求教师或助教（TA）裁决。不要反复更改标签，也不要就意图争论。教师的最终状态决定评分。

## 5. Academic integrity and anti-gaming（学术诚信与反钻空子）

- **不得**为获取额外分数而把一个根因拆成多份报告。
- **不得**移动或复用提交、为提交倒填日期（backdate），或声称证据来自另一提交。
- **不得**伪造证据、协同重复发现，或隐藏复现结果所需的信息。
- **不得**为发现或展示缺陷而违反安全边界。

伪造证据、串通、操纵提交与违反安全边界均属学术诚信问题，不获得任何审计分。
