## 确认的问题

### CF-AUDIT-01：多标签页登录被另一页清除（P1，功能缺陷）

- 位置：[AuthContext.tsx](../frontend/candidate/src/contexts/AuthContext.tsx)，clearSession第39～44行、storageChanged第63～65行。
- 条件：同一浏览器上下文有两个应用标签页，第二页即使只停留登录页也足够。
- 复现：A页登录接口返回200，B页收到token的storage事件后调用clearSession，删除共享localStorage中的新token；A页再收到删除事件，返回登录页。
- 影响：正常多标签页使用无法维持登录；此问题没有证明其他账号资料被读取，但会破坏注册/登录和会话可用性。
- 根因：清理当前标签页的React身份状态和删除所有标签页共享凭据使用同一函数。原本用于隔离旧身份的逻辑同时删掉了另一页刚建立的新会话。
- 建议：拆分“清本页缓存/废弃旧响应”和“用户主动注销并删除共享token”；storage同步应清理旧页状态并重新验证或引导该页重新登录，不能删除另一页的新token。
- 修改边界：该文件是候选人独立扩展，可在后续修复任务中维护。

### CF-AUDIT-02：默认SQL参数日志泄露简历内容（P1，隐私风险）

- 位置：[db/session.py](../backend/app/db/session.py)第4行，运行引擎硬编码echo=True；候选人路由与账号依赖复用该Session。
- 复现：隔离引擎启用同样的echo配置，通过本人简历PATCH保存虚构标记，INFO日志包含UPDATE参数中的私有简历文字。
- 影响：有权读取应用/SQL日志的人能看到本应经过简历授权的数据；并非已经证明匿名用户可通过HTTP下载日志。长参数可能截断，仍会泄露内容片段，短文本可完整出现。
- 风险条件：将当前运行配置用于真实资料或接入集中日志时成立；测试仅使用虚构标记，不读取任何个人简历。
- 建议：业务环境禁用SQL echo，启用参数隐藏/日志脱敏，避免在错误日志中重新打印请求正文或认证字段。
- 修改边界：该文件属于团队保护范围，本轮未修改。可由所有者改连接配置，或在候选人独立应用中另建安全Session适配器并通过依赖接入；不能直接修改或全局替换队友实现。

### CF-AUDIT-03：注册唯一性竞态未转换为业务错误（P2，错误处理缺陷）

- 位置：[users/service.py](../backend/app/users/service.py)第25～35行先查重再commit；[users/router.py](../backend/app/users/router.py)注册只处理ValueError；[candidate/accounts.py](../backend/app/candidate/accounts.py)第31～34行直接调用该handler。
- 复现方式：确定性模拟“查重时尚未看到另一请求的提交”，随后由真实数据库唯一约束拒绝重复邮箱写入；接口得到500，而非正常重复注册提示。
- 边界：本轮没有真实PostgreSQL同时提交测试，不能把该模拟写成已经测过实际PG并发。已确认的是IntegrityError这条真实错误分支未处理。
- 影响：数据唯一性仍受数据库保护，但并发注册同一邮箱时会向用户显示服务器故障；不能将其描述为成功创建了两个账号。
- 建议：在候选人包装层或由团队所有者处理对应唯一约束异常，回滚后确认邮箱重复，映射为现有400或明确409；其他完整性错误不能一律伪装成重复注册。
- 修改边界：原users文件保护不动，候选人accounts包装可单独适配。

### CF-AUDIT-04：推荐列表N+1查询且无分页（P2，性能缺陷）

- 位置：[service.py](../backend/app/candidate/service.py)第191～230行job_public、第235～247行list_jobs。
- 复现：监听真实SQL执行。4个有效职位执行16条SQL；增加20个虚构职位后，24个职位执行76条SQL，接口一次返回全部24条。
- 根因：逐职位读取技能、公司及本人申请标记，查询数量随职位数线性增加；资料中的大量技能也会被反复组装传给当前评分入口。
- 影响：职位增长会放大每次推荐请求的数据库开销；没有执行压力攻击，也没有据此证明服务器已被拒绝服务。
- 建议：批量读取/连接查询技能、公司和本人已申请集合，再保留统一排序。分页可另行确认；首先修复重复查询，无需改变“能查看全部有效职位”的业务目标。
- 修改边界：候选人service可维护，本轮只测量。

## 另外确认的安全边界与加固建议

这些不是额外声称已可远程利用的漏洞，需结合业务和部署决定。

1. **注销不撤销服务端Token**：关闭第二页后正常登录，再点击注销；从先前响应复制的Token调用/users/me仍得到200。当前注销只清理浏览器状态，服务器未维护撤销记录；Token仍有效至过期。若需要“注销后复制出的令牌也立即失效”，应增加服务端会话或撤销机制。仅持有浏览器退出动作、没有复制Token的第三方并不会因此自动获得权限。
2. **输入数量/长度无业务上限**：隔离PATCH成功接收140000个简历字符及1000项技能。本轮没有负载测试或DoS证明。应确定合理的正文、名称、技能数、单标签长度和请求体上限，并在后端强制校验；前端限制不能替代服务端限制。
3. **登录/注册未见应用层限流**：当前入口未配置速率限制。部署代理是否另有限流尚未验证，不能把未检查代理当成确定没有保护；公开部署前应核对暴力尝试和昂贵密码哈希请求的限制。
4. **SQLite外键配置差异**：正常运行的团队get_db引擎未显式开启SQLite foreign_keys，而独立七表make_engine和测试夹具开启了它。若使用SQLite运行原应用，需核对真实连接上的PRAGMA，不能以测试夹具约束通过替代生产连接的完整性保证。当前没有发现公开接口可直接写任意孤立行，因此列为部署风险。
