# 任务 P2：有状态模型测试——预约生命周期

**分支**：`test/P2`　**依赖**：P0 已合并　**预计**：6 小时

## 目标

用 Hypothesis `RuleBasedStateMachine` 在真实 PostgreSQL + 真实 HTTP 接口上随机生成业务操作序列，
每一步对照一个**独立的内存模型**检查不变量，并把每次运行写成事件轨迹供 P3 的 LTL 检查器使用。

## 使用的接口

| 操作 | 请求 | 成功码 |
|---|---|---|
| 投递 | `POST /candidate/jobs/{job_id}/applications`，body `{}` | 201 |
| 改状态 | `PATCH /employer/applications/{id}/status`，body `{"version": v, "status": S}` | 200 |
| 读申请人 | `GET /employer/jobs/{job_id}/applicants` | 200 |
| 建时段 | `POST /employer/interview-slots`，body `{"starts_at": ISO}` | 201 |
| 删时段 | `DELETE /employer/interview-slots/{id}` | 204 |
| 可用时段 | `GET /candidate/applications/{id}/slots` | 200 |
| 预约 | `POST /candidate/applications/{id}/booking`，body `{"slot_id": id}` | 201 |
| 删职位 | `DELETE /employer/jobs/{id}` | 204 / 409 |

`version` 来自上次读到的申请（`GET /employer/jobs/{job_id}/applicants` 行里的版本字段，以实际 schema 为准）。

## 状态机设计

- **初始化**：2 个雇主（各有公司资料、各 1 个职位）、3 个候选人（技能不同）。
- **Bundles**：`applications`、`slots`。
- **规则**（每条都要在模型里预测结果，然后与实际 HTTP 结果比对）：
  1. `apply(candidate, job)`：模型预测"已投递 → 409，否则 201 且状态 Pending"。
  2. `set_status(application, status ∈ 四个合法值)`：用正确 owner；预测 200。
  3. `set_status_wrong_owner(application)`：另一雇主 → 403；候选人 → 403；模型不变。
  4. `create_slot(employer, offset_days ∈ 1..5, half_hour ∈ 0..47)`：预测"与该雇主已有时段重叠 → 409，否则 201"。
  5. `book(application, slot)`：模型按 FP-SCHED-2 五个条件预测成功/失败码
     （本人、同雇主、Interviewing、未来且未预约、该申请无预约）。冲突码 409，跨雇主 403。
  6. `book_foreign(application, other_candidate)`：用别人身份预约 → 403 或 404（以实现为准，记录在模型里），模型不变。
  7. `delete_slot(slot)`：预测"已预约 → 409，否则 204"。
  8. `delete_job(job)`：预测"有申请或时段 → 409，否则 204"。
- **不变量**（`@invariant()`，每步后检查，以数据库/接口为准，与模型对比）：
  1. 每个时段至多一条预约；每个申请至多一条预约（直接 SQL 计数）；
  2. 已预约时段不出现在任何候选人的可用时段列表中；
  3. 每条预约对应的申请，在预约创建那一步状态为 Interviewing（模型记录）；
     之后状态改变，预约仍存在；
  4. 雇主申请人列表中每行 `match_score` 等于独立 oracle 对 (候选人技能, 职位要求) 的结果；
  5. 失败的操作不改变任何业务表的行数（每步前后做行数快照比对）。

## 轨迹输出（给 P3）

每个 Hypothesis example 结束时（`teardown`），用 `support/traces.py` 的 `write_trace` 把事件序列写到
`$ADVANCED_OUT/stateful/traces/<序号>.json`。每步之后的 `props` 至少包含：

- `applied:<app>`、`status:<app>:<Status>`、`booked:<app>:<slot>`、`available:<slot>`（该时段对其雇主名下
  任一 Interviewing 且无预约的申请可见）、`slot:<slot>`（时段存在）、`new_booking:<app>`（仅本步新建预约时）。

ID 用短别名（`a1`、`s1`），不要写 UUID。

## 规模与确定性

- `settings(max_examples=int(os.environ.get("ADVANCED_MAX_EXAMPLES", 25)), stateful_step_count=12,
  deadline=None, derandomize=True, database=None, suppress_health_check=[HealthCheck.too_slow])`
- 每个 example 开始前 TRUNCATE 业务表（显式使用 `clean_tables` 或自写）。
- 目标总耗时 < 120 秒；超出则降 `max_examples`，并在汇报里写明。

## 自检（必须做）

1. 在模型里故意把"已预约时段可删除"预测为 204，运行必须失败并给出最小操作序列。
2. 用 monkeypatch 让可用时段接口返回包含已预约时段的列表，不变量 2 必须失败。
二者验证后撤销。汇报里贴出 Hypothesis 的最小反例步骤。
