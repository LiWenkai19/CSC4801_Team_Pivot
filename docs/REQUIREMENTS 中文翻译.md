# 期末项目产品需求

本文档是本项目的规范性需求规格。每个团队都要构建下文所述的招聘与候选人匹配系统。

> **必须**（MUST）与**不得**（MUST NOT）级别的需求计入评分。**应当**（SHOULD）级别的条目为建议项，除非被另一条**必须**级需求所要求，否则不计分。**可以**（MAY）级别的条目为可选项。

## 1. Product boundary（产品边界）

### FP-ARCH-1：全栈边界

提交物**必须**是一个可在本地运行的全栈应用，包含：

- **基于浏览器的用户界面；**
- **在服务端强制执行业务规则与授权的后端服务器或 API；以及**
- **一个持久化的关系型数据库。**

应用**必须**能够在干净检出（clean checkout）后，按照 `INSTALL.md` 的说明运行。使用托管服务是可选项，且评分过程**不得**依赖托管服务。如果应用使用了外部 LLM，核心系统与自动化测试**必须**仍能在无付费凭据的情况下运行，即使用确定性的伪实现（deterministic fake）或非 LLM 的兜底方案。

## 2. Roles and authentication（角色与身份认证）

### FP-AUTH-1：账户

系统**必须**恰好支持两种应用角色：`Candidate`（候选人）与 `Employer`（雇主）。用户**必须**能够注册、登录和登出。邮箱或用户名标识符**必须**唯一。

### FP-AUTH-2：凭据存储

密码**必须**使用公认的密码哈希函数存储。明文、可逆加密，以及诸如未加盐 SHA-256 之类的通用快速哈希，均不满足本条需求。身份认证机密（authentication secrets）**不得**由 API 返回或在 UI 中渲染。


### FP-AUTH-3：服务端授权

每一个受保护的操作都**必须**在服务端强制执行角色与所有权校验；仅在 UI 中隐藏按钮是不够的。可观察的响应契约如下：

- 未认证的请求：`401 Unauthorized`（未认证）或重定向到登录页；
- 已认证但角色或所有者不符的用户：`403 Forbidden`（禁止访问）；以及
- 调用者本应有权访问、但对象不存在的情况：`404 Not Found`（未找到）。

对于非 HTTP 框架，UI 层与服务层**必须**提供等价的、可明确区分的结果。

## 3. Candidate workflow（候选人工作流）

### FP-CAN-1：候选人资料与简历

候选人**必须**只能查看和编辑自己的资料，资料包括显示名称和一份技术技能列表。技能**必须**被保存，并可供匹配函数使用。

候选人**必须**能够输入纯文本简历。应用**必须**持久化该文本，并允许其所有者查看和替换。PDF 上传与解析为可选项。简历内容为私有：只有拥有该简历的候选人可以读取或修改。任何其他候选人或雇主通过直接 URL/API 请求访问时，**必须**收到 `403`。

### FP-CAN-2：职位推荐

候选人仪表盘**必须**列出所有当前有效（未删除）的职位，为每个职位显示可见的匹配分数，并按分数从高到低排序。仪表盘**必须**包含职位名称、雇主/公司、所需技能，以及查看职位描述的入口。

### FP-CAN-3：申请

候选人**必须**能够对同一职位申请一次。新申请的状态**必须**为 `Pending`（待处理）。同一候选人对同一职位的重复申请**必须**被拒绝，且不得创建另一条记录。候选人**必须**能够查看自己每一份申请对应的职位、雇主、当前状态以及面试预约（如有）。

候选人**不得**查看其他候选人的申请，也**不得**更改申请状态。

## 4. Employer workflow（雇主工作流）

### FP-EMP-1：公司资料

雇主**必须**能够查看和编辑公司资料，资料至少包含公司名称与描述。

### FP-EMP-2：职位发布

雇主**必须**能够创建、查看、编辑和删除自己的职位发布。每份职位发布**必须**包含非空的标题与描述，以及一份所需技能列表；该列表可以为空。雇主在试图编辑、删除其他雇主的职位发布或管理其申请人时，**必须**收到 `403`。

没有申请且没有面试时段的职位**必须**可以删除。如果存在任一一类关联记录，删除操作**必须**以 `409 Conflict`（冲突）（或有明确文档说明的等价方式）失败，且职位与关联记录保持不变。

### FP-EMP-3：申请人管理

对于每一个自己拥有的职位，雇主**必须**能够查看其申请人列表，并按匹配分数从高到低排序。每一行**必须**显示候选人身份、技能、匹配分数、申请状态以及面试预约（如有）。

拥有该职位的雇主**必须**能够将申请设置为且仅能设置为以下状态之一：`Pending`、`Interviewing`（面试中）、`Rejected`（已拒绝）或 `Accepted`（已录用）。其他雇主与候选人**不得**更改该状态。

## 5. Matching contract（匹配契约）

### FP-MATCH-1：分数定义

所要求的匹配分数是一个确定性的技能重叠分数。简历文本不是输入。对候选人技能与所需技能做如下规范化：去除首尾空白、转换为小写、移除空值、去除重复项。令 `C` 与 `R` 分别为规范化后的候选人技能集合与所需技能集合：

```text
score = 100                                      when |R| = 0
score = floor(100 * |C intersection R| / |R|)   otherwise
```

结果**必须**是 0 到 100 之间的整数。候选人视图与雇主视图**必须**调用同一实现。按分数降序排序。候选人仪表盘中同分时，先按不区分大小写的职位名称、再按稳定的职位 ID 打破平局；雇主申请人列表中同分时，先按不区分大小写的候选人显示名称、再按稳定的候选人 ID 打破平局。

种子数据与单元测试**必须**包含以下示例：

| 候选人技能 | 所需技能 | 期望分数 |
|---|---|---:|
| `Python, SQL` | `Python, SQL` | 100 |
| `Python` | `Python, SQL` | 50 |
| `Rust` | `Python, SQL` | 0 |
| 任意技能 | 空列表 | 100 |

`SPEC.md` **必须**指明匹配实现的位置，并说明技能的存储方式。它可以直接引用上述公式作为判分基准，而无需另造一套评分基准（scoring oracle）。

### FP-MATCH-2：可选的 AI 增强

团队**可以**添加由 LLM 生成的解释或次级推荐，但它不带来任何替代性得分，且**不得**改变所要求的分数或排序。如果用户可控的文本被发送给 LLM，该文本**必须**被视为不可信数据，**不得**泄露提示词或机密，且数据流**必须**在 `SPEC.md` 中记录在案。可选的 AI 增强属于同伴审计的范围。

## 6. Applications and interview scheduling（申请与面试安排）

### FP-SCHED-1：可用时段

雇主**必须**能够创建和删除未来的、时长 30 分钟的可用时段。每个时段**必须**有一个所有者，以及精确的开始与结束时间，并带有无歧义、有文档说明的时区。系统**必须**拒绝非法时长、结束早于开始的取值，以及对已被预约时段的删除。已被预约的时段**不得**显示为可用。

### FP-SCHED-2：预约资格

当且仅当以下条件全部成立时，系统**必须**允许候选人预约一个时段：

- 该候选人拥有该申请；
- 该时段属于该候选人申请所对应的雇主；
- 申请状态为 `Interviewing`；
- 该时段在未来且尚未被预约；以及
- 该申请尚无已有预约。

成功的预约**必须**将候选人的申请与该时段关联，并且对该候选人和拥有该时段的雇主均可见。不满足资格的预约**必须**失败，且不得对任一记录造成部分变更。如果已预约的申请之后离开 `Interviewing` 状态，其预约**必须**保持与该申请的关联，且该时段**必须**保持不可用。

### FP-SCHED-3：原子并发

预约**必须**在数据库层面保证原子性。可使用事务加行锁、乐观并发控制、唯一性约束，或等价的数据库机制。仅靠进程内的检查是不够的。

当两名均满足资格的候选人并发尝试预约同一时段时，恰好一次尝试**必须**成功，另一次**必须**以冲突状态（HTTP `409` 或有明确文档说明的等价方式）失败并返回消息 `Slot already booked`，且此后数据库中**必须**恰好存在一条预约记录。学生**必须**为预约冲突处理逻辑编写单元测试。数据库原子性通过实现审查与运行中的系统来验证；不要求学生提供同步的多客户端测试。

## 7. Security requirements（安全需求）

### FP-SEC-1：对象访问

在请求中更改对象 ID **不得**绕过 FP-AUTH-3。授权逻辑的单元测试**必须**覆盖以下代表性边界：

1. 一个候选人不能读取或修改另一个候选人的简历或申请；
2. 一个雇主不能修改另一个雇主的职位，也不能读取其申请人列表；
3. 一个候选人不能使用另一个候选人的申请来预约时段。

此外，FP-TEST-1 还要求针对每项功能需求的单元测试；代码审查与演示可作为该证据的补充。

### FP-SEC-2：SQL 注入

所有涉及用户可控取值的数据库访问**必须**使用参数化查询、正确使用的 ORM，或等价的安全 API。禁止将原始用户输入拼接到查询中。至少一个单元测试**必须**向查询构建或数据访问逻辑传入 SQL 元字符，并验证该输入始终是绑定值而不是可执行的 SQL。代码审查与运行中的系统用于验证安全数据库 API 的使用。

### FP-SEC-3：跨站脚本（XSS）

用户可控的资料、简历、公司、职位与搜索文本在渲染为 HTML 时**必须**进行转义。如果设计上有意支持带格式的 HTML，则**必须**使用白名单净化器（allow-list sanitizer）。至少一个单元测试**必须**向渲染或消毒逻辑传入 `<script>alert(1)</script>`，并验证它不会作为可执行标记输出。

### FP-SEC-4：机密与测试隔离

仓库**不得**包含任何真实机密或个人数据。单元测试**必须**使用隔离的测试夹具（fixtures）或测试替身（test doubles），且**不得**调用真实的第三方服务。任何使用数据库的测试**必须**使用隔离的测试数据库。`.env.example` **必须**只包含占位符。

## 8. Spec-driven and AI-assisted engineering（规格驱动与 AI 辅助工程）

### FP-PROC-1：活文档规格

`SPEC.md` **必须**描述架构、数据模型及其关系、身份认证/授权设计、API 路由或服务端操作（server actions）、主要 UI 界面、匹配契约、预约事务，以及安全控制措施。需求—测试映射**必须**按照 FP-DOC-2 的规定写在 `README.md` 中，而不是写在 `SPEC.md` 中。

规格**必须**与被评分的提交（commit）一致。一份与所提交系统不符的大篇幅生成文档，在准确性上不予计分。

每位团队成员**必须**能够解释并安全地修改所提交的代码，无论其中哪些部分由 AI 生成。

## 9. Documentation, data, tests, and CI（文档、数据、测试与 CI）

### FP-DOC-1：安装说明

`INSTALL.md` **必须**列出前置依赖版本、确切的安装命令、环境变量、数据库初始化/迁移、种子数据命令、运行命令、测试命令、`Dockerfile` 的构建与启动命令，以及任何非显而易见依赖的故障排查说明。评分者在干净检出后构建仓库的 `Dockerfile` 时，**不得**需要任何未写入文档的命令或机密。

### FP-DOC-2：仓库 README

`README.md` **必须**给出简短的产品概述、架构摘要、指向 `INSTALL.md` 的快速开始链接、种子非生产用户的演示账户凭据、单元测试命令、文档索引，以及已知限制。它**必须**包含一张需求—测试映射表，覆盖本文档中的每一个需求编号，并为每项功能需求列出实现文件与学生亲笔编写的具名单元测试。非功能需求可以引用相应的验证证据。未实现的可选增强可标记为 `N/A`。

### FP-DOC-3：确定性演示数据

**必须**提供一条写入文档的命令，用于重置本地数据库并灌入种子数据。种子数据**必须**至少包括：

- 两名候选人与两名雇主；
- 两个带所需技能的职位；
- FP-MATCH-1 所要求的四个匹配示例；
- 覆盖全部四种状态的申请；以及
- 两名状态为 `Interviewing`、有资格竞争同一可用时段的候选人。

种子凭据**必须**被明确标注为本地/演示凭据。

### FP-TEST-1：自动化验证

学生**必须**为每一项功能需求亲自编写单元测试：FP-AUTH-1 至 FP-AUTH-3、FP-CAN-1 至 FP-CAN-3、FP-EMP-1 至 FP-EMP-3、FP-MATCH-1，以及 FP-SCHED-1 至 FP-SCHED-3（若实现了 FP-MATCH-2 则另加）。测试**必须**真正执行团队实际的业务逻辑，覆盖成功行为以及适用的校验、权限与冲突情形，并对可观察的结果进行断言。每项功能需求**必须**在 `README.md` 的表格中映射到具名的单元测试；照抄的示例测试或 `pass` 占位符不满足本项义务。使用 AI 辅助时，学生仍须对测试的编写、审查与讲解负责。

只要求学生提供单元测试。**必须**有一条写入文档的命令，能以非交互方式运行完整的单元测试套件，并在失败时返回非零退出码。单元测试**必须**覆盖：

- FP-AUTH-3 中未认证、禁止访问与对象缺失三种结果；
- 四个技能重叠示例与两条平局打破规则；
- FP-SEC-1 中的代表性授权边界；
- FP-SEC-2 中的 SQL 注入用例；
- FP-SEC-3 中的 XSS 用例；以及
- FP-SCHED-3 中的预约冲突处理逻辑。

演示**不得**替代所要求的单元测试。包括数据库原子性与服务端安全在内的产品需求仍然是强制性的，也可能通过代码审查与运行中的系统加以检查。使用测试替身的单元测试本身并不能证明数据库的并发行为。

## 10. Submission protocol（提交规程）

### FP-SUB-1：提交规程

每个团队**必须**提交一个指向 `main` 分支的永久性 GitHub commit URL，且该提交处的仓库**必须**能完全依靠自身的 `Dockerfile` 构建并运行。两个条件**必须**在同一个被评分提交上同时成立。任一条件不满足，即无法通过下述提交格式检查。

#### Git 提交

团队**必须**通过课程网站的提交链接提交一个永久性 GitHub commit URL，格式为 `https://github.com/<owner>/<repository>/commit/<40-character-sha>`。该 URL 同时标识仓库与确切的被评分提交。**不得**使用诸如 `/tree/main` 这类会移动的分支 URL。被链接的提交**必须**在截止时间前推送到仓库的 `main` 分支，且仓库**必须**公开，以便教师和其他团队访问。

#### Dockerfile

仓库**必须**包含一个 `Dockerfile`，能够从被评分提交构建出完整的可运行环境，使评分者与审计者能在每次提交或缺陷修复之后重新构建。**无需上传任何镜像 tar 包**——参见 [`DOCKER.md`](DOCKER.md)。该构建**必须**：

- 在被评分提交的干净检出上成功，不依赖任何未写入文档的命令或机密；
- 包含运行与测试该环境所需的每一个应用镜像与标准依赖镜像（数据库、缓存、消息代理）；
- 在运行时**无需拉取或下载任何未写入文档的容器镜像**；以及
- 不包含任何真实凭据、API 密钥、个人数据或生产数据库。

`Dockerfile`、入口脚本、迁移脚本与种子脚本**必须**保留在 Git 仓库中。Docker 镜像不保留数据库卷，因此写入文档的种子命令**必须**在启动之后初始化评分数据。镜像不能替代源码提交、CI、迁移或确定性种子数据。

在截止时间之前，团队**应当**在一台干净的机器上验证构建：

1. 克隆仓库并检出被评分的提交；
2. 构建环境（`docker build`）；
3. 使用写入文档的命令启动完整环境；
4. 运行迁移与确定性种子数据；
5. 运行所要求的自动化测试命令；以及
6. 打开浏览器 UI，完成一次写入文档的冒烟测试。

#### 提交格式检查与第二次提交

首次提交仅在以下全部条件满足时通过格式检查：永久性 commit URL 存在，且解析到公开仓库上可访问的被评分提交；所需的 CI 检查通过；仓库的 `Dockerfile` 能从该提交构建；且写入文档的启动/种子/测试流程无需下载任何未写入文档的容器镜像即可运行。

- 若首次提交通过该检查，则无提交格式扣分。
- 若首次提交未通过该检查，团队须在教师公布的截止时间前进行一次纠正性的第二次提交。若第二次提交通过，**在排名之前从 50 分的初步总分中扣除 5 分**。扣减后的初步总分用于确定团队名次。
- 若第二次提交未在截止时间前提交，或仍未通过该检查，**期末项目成绩为 0 分**，且该团队不参与正常名次换算。

## 译注

### 术语定译

- 需求分级措辞：MUST → **必须**；MUST NOT → **不得**；SHOULD → **应当**；MAY → **可以**（首次出现括注英文）。
- 状态枚举 `Pending` / `Interviewing` / `Rejected` / `Accepted` 保留英文原值，首次出现括注中文；角色标识符 `Candidate` / `Employer` 同此处理。
- requirement–test mapping → 需求—测试映射；clean checkout → 干净检出；scoring oracle → 评分基准；allow-list sanitizer → 白名单净化器；test doubles → 测试替身；fixtures → 测试夹具。
- 源文件为 Markdown 而非 PDF，无扫描伪影；score 公式代码块、HTTP 状态码、文件路径与命令均原样保留。
