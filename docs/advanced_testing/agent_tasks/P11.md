## 具体要求

### 1. 覆盖率（`coverage/entry.py`）

- 用 `coverage run --branch --source=backend/app` 分别跑：`tests/unit`（环境变量照 `tests/run_tests.py`）、
  `backend/tests`（需要 PG；用 `ADVANCED_PG_URL` 设置两个 `*_TEST_DATABASE_URL`）、
  以及 `stateful`、`differential`、`intramorphic` 三个模式目录；每组用独立 data file，最后 `coverage combine`。
- 输出：每组单独的语句/分支覆盖率 + 合并后的总数，写 `$ADVANCED_OUT/coverage/coverage-summary.json`
  与 `coverage.xml`（**不要**写成 `result.json`，会被 `run.py` 覆盖）。
- **门槛放在 `advanced` job，不放在 `unit` job**：`pytest-cov`/`coverage` 只在 `tests/advanced/requirements.txt` 里，
  不在 `requirements.lock`，`unit` job 和 Docker 镜像都没有它们；硬加 `--cov-fail-under` 会让必测命令在镜像里失败。
  在 `advanced` job 里新增一步：只对 `tests/unit` 测覆盖率并 `--cov-fail-under=<门槛>`。
  门槛 = 单元套件实测分支覆盖率**向下取整到 5 的倍数**。

### 2. 汇总脚本（`report.py`）

产物约定（前序任务已确认）：

- `run.py` 会覆盖 `<out>/<mode>/result.json`；业务结果读专用文件：
  mutation → `mutation/mutation-result.json`；apifuzz → `apifuzz/report.json`；
  stateful → `stateful/` 下 evidence 与 `traces/`；ltl → `ltl/ltl_results.json`、`refinement.json`；
  formal → `formal/booking_bmc.json` 等；differential → `differential.json`、`cross-view.json`；
  intramorphic → `defense_layers.json`、`M1.json`–`M5.json`；coverage → `coverage-summary.json`。
  文件名以实际产物为准，**先跑一次 `run.py all` 列出真实文件再写脚本**。
- junit.xml 统计用例数/失败数。
- P1、P10、P12 不是 `run.py` 模式：P1 数字来自 `python tests/run_tests.py --junitxml`；P10、P12 从其仓库内
  JSON / 文档读取（`experiments/llm_blind/results.json`、`mutation/results.json`；P12 只链接文档）。

`report.py <out目录> [--unit-junit FILE]` 生成 `docs/advanced_testing/ADVANCED_REPORT.md`，结构：

1. **一页摘要**：一段话 + 总表（技术 | 讲义出处 | 规模 | 结果 | 证据文档）。
2. **方法论**（手写段落，可放在脚本模板里）：独立 oracle；每个 oracle 都做"故意引入错误 → 变红"的自检；
   空真/可达性检查（P3、P5）；确定性（固定种子、逐字节可复现）；安全边界（一次性 PG、产物出仓、只连本机）。
3. **每项技术一节**：讲义出处、要回答的问题、命令、关键数字（**从 JSON 读，不手填**）、亮点（用上表"亮点"列，
   引用对应文档里的具体反例/表格）、局限、详细文档链接。
4. **发现与闭环**：P8 的契约缺陷从发现到修复的全过程（需求 → 测试 → 失败 → 修复 → 重跑），对应 L14 slide 29。
5. **局限与未做**：形式化证明的对象是抽象模型/规格；BMC/归纳之外的并发由数据库保证；
   变异分数是同口径前后对比；`pip-audit` 只扫运行时锁文件；本地 PG 版本差异（见 §3）。
6. 页脚：commit SHA、生成时间、证据来源（CI run 号或本地目录）。
