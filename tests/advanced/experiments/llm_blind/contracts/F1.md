# Contract F1 — `app.employer.matching.match_score`

**Status of this file: written by the experiment owner before any generated test
existed. It is the only behaviour description given to the generator agent.**

- Normative sources: `docs/REQUIREMENTS.md` §5 **FP-MATCH-1**; `SPEC.md` §“Matching
  Algorithm and Skill Storage”.
- Signature (given by the project brief):
  `def match_score(candidate_skills: list[str], required_skills: list[str]) -> int`
- Import path: `from app.employer.matching import match_score`
- Docstring (verbatim as far as the file encoding allowed): “按 FP-MATCH-1 公式计算
  0-100 的技能匹配分。”

## 1. Inputs

Two Python `list[str]` values, in this order:

1. `candidate_skills` — the candidate profile's skill names.
2. `required_skills` — the job posting's required skill names.

Each list may be empty and may contain duplicates, mixed case, surrounding
whitespace, or empty strings. Elements are declared `str`; no other element type
is part of the contract.

## 2. Normalisation (applies to each list independently)

1. Remove leading and trailing whitespace (`str.strip()` semantics: spaces, tabs,
   newlines; internal whitespace is preserved).
2. Convert to lowercase (`str.lower()` semantics, not `casefold()`).
3. Drop entries that are empty after step 1.
4. Remove duplicates.

Let `C` and `R` be the resulting sets of strings. Normalisation is part of the
contract: two inputs that normalise to the same `(C, R)` must return the same
score.

## 3. Output

A Python `int` (not `bool`, not `float`) in `[0, 100]`:

```text
score = 100                                      when |R| = 0
score = floor(100 * |C ∩ R| / |R|)               otherwise
```

“floor” is mathematical floor on non-negative values; the equivalent integer
operation is `100 * k // n` with `k = |C ∩ R|` and `n = |R|`.

The function is pure and deterministic: no I/O, no mutation of the input lists,
no side effects. For inputs satisfying the declared types it raises no exception.

## 4. Required examples (from FP-MATCH-1, independent hand calculation)

| Candidate skills | Required skills | Arithmetic | Expected |
|---|---|---:|---:|
| `["Python", "SQL"]` | `["Python", "SQL"]` | k=2, n=2; 100*2//2 = 100 | **100** |
| `["Python"]` | `["Python", "SQL"]` | k=1, n=2; 100*1//2 = 50 | **50** |
| `["Rust"]` | `["Python", "SQL"]` | k=0, n=2; 100*0//2 = 0 | **0** |
| any skills | `[]` | n = 0 → special case | **100** |

A second hand calculation for normalisation: candidate
`[" SQL ", "sql", "Python", ""]`, required `["SQL", "  ", "python "]`:
`C = {"sql", "python"}`, `R = {"sql", "python"}`, `k=2, n=2`, expected **100**.

## 5. Boundaries and partitions

- **Valid / ordinary:** partial overlap; full overlap; disjoint sets.
- **Boundary:** `R` empty (100 regardless of `C`, including `C` empty); `C` empty
  and `R` non-empty (0); `C ⊇ R` with `|R| > 0` (100); one missing skill flips the
  floor boundary when `|R|` divides 100 unevenly (e.g. `|R|=3`, `k=2` → `66`).
- **Normalisation:** whitespace-only entries, duplicates, case variants, empty
  strings; all must not change the result.
- **Invalid:** inputs outside `list[str]` are outside the contract. Do not invent
  expected exceptions or result values for them; record them as an ambiguity.
- **Non-ASCII:** `str.lower()` is the contract; e.g. `"C++"` → `"c++"`,
  `"机器学习"` is unchanged. Do not assume `casefold()` behaviour.

## 6. Ambiguities to record

1. No error behaviour is specified for `None`, strings instead of lists, or
   non-string elements; contract says undefined, so no test should demand a
   particular exception.
2. “Lowercase” is `str.lower()`, not Unicode case folding (`İ`, `ß`, `SS` must not
   be treated as equal unless `str.lower()` makes them equal).
3. Internal whitespace is preserved; `"data science"` and `"data  science"` are
   different skills.
4. `bool` is a subclass of `int` in Python; the contract only constrains the
   *return* to be `int`, and the natural implementation returns a plain `int`.
   Assert `type(result) is int` rather than `isinstance(result, int)` if the
   generator wants to exclude `bool`.

## 7. Independent oracle rule for the generator

Every expected score in the generated tests must be derived from this contract
(or from the table above) and the arithmetic must be written next to the
assertion. The generator must not call `match_score`, `normalize_skills`, or any
other application function to compute an expected value.
