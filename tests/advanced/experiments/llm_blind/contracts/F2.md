# Contract F2 — `app.candidate.service.book`

**Status of this file: written by the experiment owner before any generated test
existed. It is the only behaviour description given to the generator agent.**

- Normative sources: `docs/REQUIREMENTS.md` **FP-SCHED-2**, **FP-SCHED-3**;
  `SPEC.md` §“Interview Scheduling and Booking Transaction”.
- Signature (given by the project brief):
  `def book(session: Session, user: User, application_id: uuid.UUID, slot_id: uuid.UUID) -> BookingPublic`
- Import paths:
  - `from app.candidate.service import book, NotFoundError, ForbiddenError, ConflictError`
  - `from app.candidate.schema import BookingPublic`
  - `from app.employer.model import Application, ApplicationStatus, InterviewSlot, Job, Booking`
  - `from app.users.model import User, Role`
- Docstring (verbatim as far as the file encoding allowed): “创建面试预约，并按有效期与
  唯一约束防止并发重复写入。”

The router calls this function only for an authenticated candidate. Role and HTTP
status mapping are outside this function; the function's public failure surface is
three `ValueError` subclasses exported from `app.candidate.service`:
`NotFoundError`, `ForbiddenError`, `ConflictError`.

## 1. Inputs

- `session` — a SQLModel `Session` (in unit tests, a session double; no real
  database may be opened).
- `user` — the authenticated candidate account (`User`); its `id` is the candidate
  ID used for ownership.
- `application_id` — `uuid.UUID` of the application to book.
- `slot_id` — `uuid.UUID` of the interview slot to book.

The candidate profile, the application row, the job row, the slot row and any
existing booking are supplied by the session.

## 2. Eligibility (FP-SCHED-2) — every condition must hold

State read from the session:

- `application`: `Application(id, candidate_id, job_id, status, version, ...)`
- `job` referenced by `application.job_id`: `Job(id, employer_id, ...)`
- `slot`: `InterviewSlot(id, employer_id, job_id, starts_at, ends_at)`
- existing `Booking(application_id, slot_id)` rows, if any

Checks, in contract order (order affects which error wins when several are false):

1. Application exists. Missing → `NotFoundError`.
2. `application.candidate_id == user.id` (candidate owns the application).
   Wrong candidate → `ForbiddenError`.
3. `application.status == ApplicationStatus.Interviewing`. Any other status
   (`Pending`, `Rejected`, `Accepted`) → `ConflictError`.
4. Application has no existing booking → otherwise `ConflictError` with message
   `Application already booked`.
5. Slot exists. Missing → `NotFoundError` with message `Slot not found`.
6. Job referenced by the application exists. Missing → `NotFoundError` with
   message `Job not found`.
7. `slot.employer_id == job.employer_id` (slot belongs to the employer of the
   application's job). Different employer → `ForbiddenError` with message
   `Slot belongs to another employer`.
8. `slot.starts_at` is strictly in the future (UTC). Past or exactly now →
   `ConflictError` with message `Slot is in the past`.
9. `slot.ends_at - slot.starts_at == 30 minutes` exactly. Other duration →
   `ConflictError` with message `Slot must last 30 minutes`.
10. Slot is not already booked → otherwise `ConflictError` with message
    `Slot already booked`.
11. `slot.job_id` is `None` or equal to `application.job_id`. Another job →
    `ConflictError` with message `Slot is reserved for another job`.

Booking conflict handling (FP-SCHED-3): the database has unique constraints on
`booking.application_id` and `booking.slot_id`. If the commit raises an
`sqlalchemy.exc.IntegrityError`, the function must roll back and raise
`ConflictError` with message `Slot already booked`; a failed booking must not leave
a slot assignment or a booking behind.

## 3. Success behaviour

When all checks pass:

1. Set `slot.job_id = application.job_id`.
2. Insert exactly one `Booking(application_id=application.id, slot_id=slot.id)`.
3. Commit once.
4. Return a `BookingPublic` whose `slot_id` is the slot's ID and whose
   `starts_at`/`ends_at` equal the slot's start/end. (`BookingPublic` fields:
   `booking_id`, `slot_id`, `starts_at`, `ends_at`; `booking_id` is the new
   booking's ID.)
5. The booking is visible to both parties through the same persisted row.

The function does not change the application's status or version.

## 4. Rejection behaviour (L14 slide 26 obligation)

Every rejected call must:

1. raise the **exact** exception class above (not a bare `ValueError`, not a
   different subclass);
2. leave observable state unchanged:
   - `session.commit` was **not** called;
   - no `Booking` row was persisted;
   - `slot.job_id` is unchanged;
   - the application's status/version are unchanged;
3. if the function staged a write (for example `session.add`) or attempted a
   commit before failing, it must call `session.rollback`. For a pure validation
   rejection that stages nothing, “state unchanged” is the obligation; a rollback
   call is not required by the contract but is acceptable.

The generator must snapshot the whole relevant state before the call and compare
afterwards, instead of only asserting “it raised”.

## 5. Hand-calculated scenarios (three expected values)

Use these IDs and timestamps; the expected outcome is computed from the contract
above, not from the implementation.

**S1 — eligible booking succeeds.**
`user.id = u1`; `application = (id=a1, candidate_id=u1, job_id=j1,
status=Interviewing, version=1)`; `job = (id=j1, employer_id=e1)`;
`slot = (id=s1, employer_id=e1, job_id=None, starts_at=2099-01-01T10:00:00Z,
ends_at=2099-01-01T10:30:00Z)`; no existing booking.
Expected: return `BookingPublic(slot_id=s1, starts_at=10:00Z, ends_at=10:30Z)`;
slot.job_id becomes `j1`; one `Booking(application_id=a1, slot_id=s1)` added;
one commit.

**S2 — wrong status is rejected.**
Same as S1 but `application.status = Pending`.
Expected: `ConflictError`; commit count 0; application unchanged; slot.job_id
stays `None`.

**S3 — another candidate's application is forbidden.**
Same as S1 but `application.candidate_id = u2` while `user.id = u1`.
Expected: `ForbiddenError`; commit count 0; state unchanged.

Additional boundaries the generator should cover: slot in the past; 29/31-minute
slot; already-booked slot; slot reserved for another job; missing application;
missing slot; missing job; commit raising `IntegrityError`.

## 6. Test-double recipe (allowed; no real database)

The unit suite's style is `MagicMock(spec=Session)` plus an autouse guard that
forbids `Engine.connect`. Two equivalent options are acceptable:

1. Use the helper `make_session(...)` in
   `tests/advanced/experiments/llm_blind/generated/session_double.py`. It answers
   both `session.get(Model, id)` and `session.exec(select(Model) ...)` lookups from
   the objects you pass, returns empty results for `Booking` queries unless you
   configure a booking, and assigns IDs to added `Booking` rows.
2. Build `MagicMock(spec=Session)` yourself. Make **every** result chain empty by
   default (`.first()`, `.one_or_none()`, `.all()`, `.scalars().first()`), because
   the service may use any of them to check existing bookings. Configure
   `session.get.side_effect` and `session.exec.side_effect` to return your objects;
   do not rely on call order.

Never execute a real query; a real database connection is a test failure.

## 7. Ambiguities to record

1. Exception messages are public user-facing text but are not part of
   `REQUIREMENTS.md`/`SPEC.md` verbatim for every path; the messages above are the
   service contract supplied with this experiment. Tests should assert the class
   always and the message where this contract fixes one.
2. For pure validation rejections the service may or may not call
   `session.rollback`; the invariant is “no commit and no observable mutation”.
   A blanket `rollback.assert_called()` is only justified when a write was staged
   or a commit was attempted.
3. Check order is observable when several checks fail at once. The contract order
   above is normative for this experiment; tests should construct single-fault
   states unless they explicitly test precedence.
4. HTTP status mapping (`403`/`404`/`409`) is the router's job and is not asserted
   by service-level tests.
