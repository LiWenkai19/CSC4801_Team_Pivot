# 前端页面开发

先与用户明确一条具体、连贯且可验证的页面交互逻辑，再在现有架构内实现有限范围的改动。以下需求澄清与范围限制是用户明确要求，不能用先搭骨架、自动拆任务或扩大辅助代码来绕过。

## 1. 默认交付范围：一个页面，或至多 15 个特定函数

修改前选择并说明本次采用的模式；两种额度不能叠加，上限不是必须用满的目标。

| 模式 | 默认上限 | 允许的必要关联改动 |
| --- | --- | --- |
| 页面模式 | 新增或实质开发一个明确页面 | 该页面必需的专用表单/弹窗、展示组件、API 封装、类型、必要基础样式、路由接入及验证 |
| 函数模式 | 新增或实质修改不超过 15 个职责明确的函数 | 这批函数必需的类型、导入、调用接线及验证；不得变相实现多个完整页面 |

- 页面按具有独立入口和完整交互目的的界面计数；改名为组件、弹窗、Tab 或不注册路由，仍不能把多个独立页面算成一个。专用弹窗只有服务于本次明确逻辑时才属于关联范围。
- 页面模式的限制是一个页面；15 个函数是函数模式的上限，不额外强加给单页模式。一个页面也不能被扩成包含多个业务流程的整套管理系统。
- 函数模式先列出 `文件路径 + 函数名/语义名称 + 职责 + 输入输出`。数量包括新增和实质修改的组件函数、API 函数、Hook、事件处理器、辅助函数及有独立逻辑的嵌套/匿名回调，按实际函数实体去重；不能只数导出函数。
- 纯调用已有函数的 JSX 绑定、类型声明、CSS、导入和机械接线不单独计函数；匿名化业务逻辑、拼接巨型函数或把辅助函数移到别处不能规避计数。必要的新增测试辅助函数也纳入函数清单。
- “完成用户管理”“把报销功能做好”“全部继续”等功能性表达不自动扩大额度。只有用户明确指定批量页面/函数或明确扩大本次范围，才可突破默认上限；逻辑澄清要求仍然有效。
- 限制针对一次已明确的开发任务，不能通过多次工具调用、内部子任务、自动开启下一轮或委派代理绕过。达到本次边界后交付并等待新指令。
- 发现必要关联改动会超出范围时，先说明具体超出项并提问；不以“顺便修复”扩大任务。

### 先跑通最简单的逻辑，美化另行开展

- 默认选择满足已明确需求的最简单实现，只完成当前交互闭环；不自行添加可选功能、复杂抽象或额外交互。必要的输入校验、权限处理、错误提示和结果更新仍须完整。
- 功能开发阶段使用原生表单、按钮、列表和已有组件，以能操作、能看清结果为准；仅添加保证可读、可点击和流程可用的基础样式，不开展配色、装饰、动画或整体布局美化，也不为美化引入依赖。
- 澄清问题聚焦业务流程，不在功能阶段询问装饰性视觉偏好。逻辑完成后先实际验证并交付；页面美化等待用户单独提出任务，不在本轮自动追加。功能验收以逻辑是否跑通为准。

## 2. 功能描述先问清，逻辑明确前禁止改任何代码

**先判断用户给出的是业务能力，还是已经明确的实现任务。** “做一个发票上传页”即使只有一个页面，也可能仍是功能描述；页面名称或一句“你看着做”不能补齐业务规则。

功能描述的处理方式：

1. 只读查看规范、相关页面、组件、API、类型及可用的接口契约，区分“用户已说明”“现有实现可确定”“仍需用户决定”。
2. 用简短候选流程帮助用户选择具体逻辑，例如“选择记录 → 填写字段 → 提交 → 显示结果”；明确标注建议和未知项，不能把推测写成已决定的需求。
3. 每轮优先提出 1～3 个影响流程的问题，给出简短选项和差异。先问角色/目标、入口/动作、数据与结果，再问会影响实现的异常分支；不要一次抛出无关问卷。
4. 必须利用用户实际回答收敛逻辑：复述新增约束，修正先前方案，只追问剩余的关键分歧。未回复、时间经过或用户只回答了部分问题，都不等于其余选项获同意。
5. 当至少一条本次要实现的具体逻辑形成完整闭环，且本次范围内影响业务含义、权限、数据或兼容性的关键问题均已明确，才进入实现。不能因为其中一条流程明确，就顺带实现其他待澄清流程。

闭环应能回答以下问题；现有代码、接口契约和用户先前回答已提供答案的，不重复询问。

| 项目 | 必须明确的内容 |
| --- | --- |
| 目标与入口 | 谁在什么位置，为完成什么任务触发哪个页面、弹窗或函数 |
| 数据与输入 | 展示/编辑哪些字段，数据来源、初始值、必填项和有效性规则是什么 |
| 动作与状态 | 用户依次做什么；初始、加载、可编辑、提交、成功/失败如何变化 |
| 接口与权限 | 调用哪个已有接口，输入输出是什么，登录/角色/记录归属如何限制；纯展示可注明不适用 |
| 结果与恢复 | 成功后更新哪里、是否关闭/跳转；失败如何提示、保留输入和重试 |
| 边界与验收 | 本次具体页面或函数清单；用什么输入与可见结果判断完成 |

- 逻辑未明确时，不修改任何业务代码、组件、API、类型、样式、路由、测试、依赖或配置；也不先搭骨架、安装依赖、生成脚手架或调用会写入业务数据的接口。此时仅做只读分析与问答；用户另行要求的需求文档可单独整理。
- 用户已经给出具体页面/函数、行为、契约和验收条件时，读取代码核实后直接推进，不机械重复请求确认。命名、缩进等不改变业务含义的细节沿用项目约定。
- 新接口不存在或返回契约未知时，先问清如何衔接。不得自行虚构后端实现；仅在用户明确要求静态原型且交互逻辑已明确时使用标注清楚的模拟数据，并说明尚未完成真实接口验证。

逻辑明确后的实现说明可使用以下短格式，不要求用户填写模板：

```text
本次模式与范围：一个页面 / N 个特定函数（列出路径与名称）
交互逻辑：角色与入口 → 输入及校验 → 动作与状态 → 结果及失败恢复
接口与权限：已有契约、允许操作、无权时行为（或不适用）
涉及文件与用途：页面 / 专用组件 / API / 类型 / 必要接入
验收：正常流程 + 本次涉及的关键异常分支
```

若仍有关键未知项，输出已知逻辑和问题并保持只读；不要输出这份说明后自行开始实现。

## 3. 根据项目现状落位，保持职责分层

- 开始时读取适用的 `AGENTS.md`、`CLAUDE.md`、前端规范、模块说明、依赖清单及相关代码；检查工作区原有改动。文档与代码冲突时说明差异，结合用户当前指令核对，不照抄旧进度或旧权限表。
- 在 SYManage 或需要理解这套结构的 React 项目中，按需阅读 [工作区架构与代码规律](references/workspace-layering.md)。其中是有来源的项目实例；跨项目时映射职责到实际目录，不强制沿用框架版本、文件名或业务角色。

| 层级 | 职责与放置原则 |
| --- | --- |
| 应用入口与路由 | 初始化 Provider、注册页面、接入已有登录守卫；不承载表单或业务请求流程 |
| `pages/<feature>/` | 按业务组织页面，协调数据、页面状态、权限展示和子组件；专用表单/弹窗就近放置 |
| `components/` | 已有共用展示与交互组件；通过明确 Props 接收数据和回调，避免绑定某页的私有流程 |
| `contexts/` 或现有状态层 | 登录态及确实需要跨页面共享的状态；单页输入、弹窗和临时错误就近维护 |
| `api/<feature>_api.*` | 将具体业务动作映射到接口路径、请求参数与响应类型；不操作页面状态或导航 |
| 公共请求层 | 统一请求、认证头、序列化/上传及错误解析；不在每个页面重复 `fetch` |
| 类型与样式 | 共享契约沿用现有类型位置，组件私有 Props 就近声明；样式沿用现有体系和作用域 |

- 调用方向保持：页面/业务组件 → 业务 API → 公共请求层；页面 → 展示组件，展示组件经回调通知父级；Context 可调用 API，API 不反向依赖 UI 或 Context。
- 不为一个简单页面建立新的全局状态库、请求库、通用组件库或额外架构层；确有重复职责才抽取。其他技术栈沿用其等价机制，不能为了使用本 skill 改写项目框架。
- 修改前说明文件与用途，先阅读当前文件；保留未提交的改动，避免整文件替换或格式化无关代码。

## 4. 按明确的数据流实现页面

- 页面保存服务端原始数据与必要的本地 UI 状态；筛选、分组等可推导结果在渲染阶段计算，只有需要时才缓存，不用额外 Effect 同步第二份 state。
- 父页面拥有页面数据与弹窗开关；子组件使用有类型的 `onClose`、`onSubmit`/`onSuccess` 等回调表达结果。写入成功后按已明确规则更新本地数据或重新请求，关闭和成功是不同事件，不把取消等同于成功。
- 异步流程清理旧错误，展示对应区域的加载/空态/错误/成功结果；提交期间阻止重复提交，结束时恢复状态。失败保留用户应保留的输入，清空时机遵循约定流程。
- 加载或失败只影响所属区域；已有表单或弹窗需要保持时，避免父级提前返回导致其卸载和输入丢失。复杂编辑流程明确状态及允许动作，保留后端枚举的真实含义。
- 更新数组/对象使用不可变更新；列表使用稳定业务标识作为 `key`。Hooks 的调用顺序稳定，Effect 依赖符合实际数据流。
- 登录状态优先复用既有 Context/守卫，区分登录检查中与未登录。前端角色判断控制展示和交互，真实授权以服务端契约为准，不把隐藏按钮当作后端授权。
- 接口字段名、可空值、联合响应及金额/日期等类型以实际契约核对；API DTO 与 UI 输入需要转换时显式转换，不用 `any` 或强制断言掩盖不匹配。
- 文件上传复用已有上传封装，`FormData` 不手写 multipart boundary。JSON、空响应、文件下载各自按真实响应处理，不能假设所有请求都返回 JSON。
- 类型使用项目支持的写法。此工作区表单沿用 `React.SubmitEvent<HTMLFormElement>`，其他事件明确目标元素；其他项目先核对实际类型定义，不照搬此版本要求。
- 沿用现有命名、导入、样式与中文交流习惯；新增或修改的关键组件、处理器和业务辅助逻辑用简短中文说明目的与约束，不把学习性解释塞进面向产品用户的界面。

## 5. 在本次范围内验证并交付

- 根据真实 `package.json` 与工具配置运行适用检查。SYManage 前端使用 `npm run build`（TypeScript + Vite）和 `npm run lint`（Oxlint）；其他项目采用自身命令。
- 验证已明确的正常路径和相关边界：加载、空数据、输入错误、请求失败、重复提交、成功后刷新/关闭/跳转；涉及登录和权限时核对对应行为。根据改动选择必要场景，不机械生成全套测试工程。
- 优先使用已有测试设施。复杂状态转换、数据转换或容易回归的交互可补针对性测试并运行；简单样式或低影响接线不为覆盖字面实现新增测试基础设施。
- 可用的页面运行/浏览器验证应覆盖关键可见行为；仅 build/lint 通过不能称为交互或后端联调通过。没有实际运行的项目明确列为未验证。
- 全项目检查被既有未完成代码阻塞时，记录具体命令、错误位置及本次可验证范围，不修复范围外文件来凑通过，不把局部结果说成全量通过。
- 重新读取最终文件、核对 diff，交付本次行为、全部改动文件与关键行号链接、实际检查结果及剩余问题；函数模式同时报告实际函数清单和数量。
- 项目已有进度记录要求时，按其位置同步本次事实与未完成事项；不把旧路线图中的任务自动纳入范围。交付当前单位后等待下一条开发指令。

## 6. 边界判定示例

- “做一个活动管理系统”：只读定位现状，询问先完成哪个角色的哪条流程；不创建活动页面、API 或占位组件。
- “做一个发票上传页面”：询问上传后直接保存还是先核对、字段/关联记录从哪里来、成功后如何处理；根据回答继续收敛，不因已指定单页就开始写。
- “只修改 `handleItemChange`，按条目 ID 更新名称并保持其他字段不变”：读取函数、类型与调用方后，逻辑无歧义即可按函数模式实施，不重复询问整页需求。
- “按现有契约实现成员列表页，仅展示姓名；挂到现有登录守卫；加载、错误、空列表各自提示”：核对已有列表接口与类型，满足闭环即可按页面模式实施；不增加编辑、删除或批量导入。
- “把这 18 个函数都实现”：用户若明确一次实现清单中的 18 个函数，属于扩大数量范围；每个函数的关键逻辑仍要明确。代理自己推导出的 18 个函数不属于批量授权。
