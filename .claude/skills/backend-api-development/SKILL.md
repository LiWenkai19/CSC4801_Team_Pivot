# 后端接口开发

以一个明确、可验证的接口作为默认交付单位。以下八项为用户硬性要求，不得因赶进度、接口简单或旧代码存在反例而省略。

## 1. 默认一次只实现一个接口

- 没有用户明确要求批量实现时，每次开发任务/交付轮次最多新增或修改一个接口及其必要关联函数；不能自行分成多个子任务或交给多个代理来绕过限制。
- 接口按 `HTTP 方法 + 完整路径` 计数；同一路径的 GET 和 POST 是两个接口，多个路由装饰器注册的别名也分别计数。
- 关联范围包括该接口必需的 model、schema、service、权限依赖、路由注册、迁移、测试和进度记录；不顺手实现其他接口或重构整个模块。
- “实现人员管理”“完成报销功能”等功能描述不等于批量授权；用户明确要求“一次实现这三个接口”等才可突破数量限制，并逐个落实下面的规则。
- 完成当前接口后给出候选下一步，等待后续指令；不能因为路线图列了多个接口就自动继续。

## 2. 功能描述必须先细化，未明确接口禁止改代码

- 如果用户描述的是业务能力或流程，先只读查看现有实现、需求和进度，提出接口候选及关键问题，直到确定本次具体接口。
- 具体接口至少明确：业务模块、HTTP 方法与路径、请求字段和校验、响应结构、身份及权限、关键业务规则、错误行为。无需拘泥于文档格式，已有代码与用户明确指令可以提供这些信息。
- 在这之前不得修改任何代码，包括 model/schema、辅助函数、测试、迁移、依赖配置和“先搭架子”；也不得执行产生业务写入的命令。不能自行挑选一个接口，把它写出来后再请用户确认。
- 此阶段允许读取和讨论；若已有实质性分析进展，允许只更新模块内的 Markdown 需求/进度文档，不创建代码骨架。模块未确定时先不创建目录，待明确归属后补记。
- “帮我实现 `GET /users/me`，返回现有 UserPublic，要求登录”等明确请求，可在读取代码和补足无歧义细节后直接推进；不要重复索取已经给出的授权。影响业务含义、权限或兼容性的未知项必须先问清楚。
- 修改前简要说明本次接口、准备改动的文件和用途。

## 3. 按业务功能组织模块

优先定位 `app/<feature>/`，按下面的职责放置代码；目录以项目实际后端根目录为准。

| 文件 | 职责 |
| --- | --- |
| `model.py` | SQLModel 数据库表、字段约束及关系 |
| `schema.py` | 请求与响应的数据结构、字段校验 |
| `service.py` | 数据库操作、业务规则及事务 |
| `router.py` | API 路由、依赖注入及 HTTP 错误转换 |
| `security.py` | 项目需要时集中处理密码、Token 等安全工具 |

- 不为凑齐文件创建空模块；工具函数按所属业务归类，跨模块共享能力才放公共模块。
- 密码哈希和 Token 工具不散落在 router/service；业务解析、表单生成等独立能力可放业务模块内的专用文件。
- 修改前阅读现有文件，保留用户尚未提交的改动，避免覆盖或格式化无关代码。

## 4. 每段代码交付必须报告全部改动与行号

- 完成一段可交付代码后，向用户说明每个新增、修改或删除文件的用途，包括关联函数、测试、迁移、依赖配置与进度文档；不得只汇报 router。
- 重新读取最终文件并核对 diff，再给出关键函数/类型的准确行号和可点击文件链接，例如 `[service.py](/absolute/path/service.py:42)`。不能使用修改前的旧行号。
- 删除内容说明原路径、删除对象和原因，不伪造已经不存在的行号；整体删除的文件无需提供可点击行号。
- 报告接口行为、测试命令与结果、未解决的问题；区分本次改动与工作区原有改动。可在一个回复中汇报多段相关代码，无需每写一行就发消息。

## 5. 每个完成的函数必须有简短中文注释

- 所有本次新增或实质修改的函数（含路由、业务函数、依赖、嵌套函数、测试和 fixture）都必须有中文说明，优先使用函数体首行的一句 docstring。
- 简要解释函数的业务目的；有关键约束时补充一句，不重复代码逐行含义。例：`"""查询本人发票，拒绝访问他人记录。"""`。
- 保留有价值的既有说明；不要为补注释遍历修改未涉及的旧函数。复杂判断仅在必要位置增加简短中文注释。

## 6. 严格遵循分层

- 工作前读取项目适用的 `AGENTS.md`、`AGENT.md`、`CLAUDE.md`、模块需求和进度，核对真实代码。SYManage 或同类 FastAPI/SQLModel 项目另读 [工作区分层参考](references/workspace-layering.md)；这是提取的参考，不替代当前项目事实。
- router 处理 HTTP 入参、依赖注入、调用 service、输出响应和错误转换；不得直接编写数据库查询、提交事务或承载核心业务流程。
- service 接收显式业务参数、当前操作者和 Session，处理业务校验及持久化；不使用 `Depends`、`HTTPException`、HTTP 状态码或 Request/Response 来表达业务逻辑。
- model 不承载路由逻辑；schema 不进行数据库写入。依赖方向保持 `router → service → model/security`，schema 可被 router/service 使用，避免循环导入和 service 反向导入 router。
- Session 由统一依赖提供；事务边界位于 service，多个相关写入应具有原子性，失败时正确回滚，避免辅助函数提前提交破坏原子性。
- 身份认证与通用角色检查放项目统一依赖层；记录归属、状态流转等业务权限在 service 校验，不能只检查角色而放任跨用户访问。
- 沿用项目的业务异常约定；本工作区通常为 service 抛 `ValueError`、router 转 HTTP 错误。不同错误语义需要区分时，在当前接口范围内使用明确的异常子类/类型，不靠字符串包含关系猜测状态码。
- 旧实现违反分层时，不把它当作新代码模板；仅调整当前接口必需的相关代码，并报告影响。不要借此迁移所有旧接口。

## 7. 每有实质进展同步模块内进度文档

- 开始前读取已有模块进度；优先沿用现有文件，否则在 `app/<feature>/PROGRESS.md` 创建。不得只写工作区根目录日志代替模块记录。
- 需求明确、代码实现、测试完成、发现阻塞或解决问题等每个实质节点都要及时更新，不能到最后一次性回填。没有新事实时不制造重复日志。
- 记录当前接口、状态、已完成事项、涉及文件/函数、实际验证命令和结果、剩余问题及下一步；日期按用户时区，后续更新保留重要历史。
- 使用“待细化 / 待实现 / 待验证 / 验证失败 / 验证通过 / 阻塞”等准确状态；代码写完不等于验证通过。
- 项目另外要求全局进度时，同步简要状态并链接模块记录；稳定架构留在规范文档中，不混入进度日志。

## 8. 每个接口同步测试并直接运行验证

- 新增或修改接口时同步新增/更新自动化测试；沿用项目测试目录，没有约定时使用 `backend/tests/<feature>/test_<endpoint>.py`。不能只给测试建议或要求用户自行运行。
- 在确定的项目解释器/虚拟环境中实际运行该接口测试、受关联改动影响的回归测试，以及项目配置的相关静态检查。只有必要时扩大范围；禁止用全库自动修复掩盖无关问题。
- 测试通过 HTTP 路由验证状态码、响应内容及必要的数据库变化；mock service 的路由测试不能作为接口业务完成的唯一证据。

| 场景 | 必须验证的内容 |
| --- | --- |
| 正常请求 | 正确输入、允许的身份、响应结构和业务结果 |
| 非法参数 | 缺字段、错误类型/格式、业务边界；失败无意外写入 |
| 未登录 | 受保护接口缺失 Token 被拒绝；认证相关接口另测无效/过期 Token |
| 越权 | 角色不足；涉及记录归属时测试访问他人的资源 |
| 资源不存在 | 不存在的有效 ID 或关联记录得到约定错误，不产生脏数据 |

- 每个接口都逐项评估上表。公开接口应测试匿名请求按设计成功；没有角色限制或不查询特定资源的场景可标为“不适用”，但必须解释原因，不能跳过评估。
- 认证/权限测试必须实际经过对应依赖。可以覆盖数据库依赖使用隔离数据；不能在所有测试中替换 `get_current_user` 为成功用户后声称已验证未登录。
- 测试仅连接隔离测试数据库，文件写入使用临时目录；必要时隔离 lifespan 初始化。确认测试配置在应用/engine 导入前生效，不能连接真实业务库、执行种子脚本或创建真实管理员来凑测试数据。
- PostgreSQL 特有类型、锁、约束或迁移行为必须在隔离 PostgreSQL 环境验证；SQLite 或纯 mock 的结果只能证明其覆盖范围，不能宣称生产数据库行为已验证。
- 缺少测试基础设施时只补当前接口所需的最小 fixture/依赖。运行失败要定位并修复本次问题，重新运行受影响检查；环境阻塞则记录命令、错误、原因和所需条件，不标记接口完成，不伪造通过或默认忽略 skip。

## 补充策略

- **接口契约与兼容性：** 实现前写清字段、状态码和 response_model；不得在未说明的情况下破坏已有接口。涉及前端类型时检查调用方，只有当前接口兼容所必需的内容纳入改动。
- **安全与数据一致性：** 请求参数不能替代可信的当前用户；响应不得泄露密码哈希、密钥或无关 Token，认证接口按契约返回授权签发的 Token。写入接口按实际风险处理唯一性冲突、事务和幂等，不为每个简单接口引入复杂架构。
- **模型变更与迁移：** 表结构改变时同步迁移、核对模型注册，审查自动生成结果并在隔离库验证；不自动对真实业务库执行破坏性操作。
- **如实交付：** 最终报告包含本次全部改动的行号链接、测试覆盖与不适用说明、实际验证结果、进度文档位置和遗留问题。发现范围外问题先报告，不顺手扩展实现。

## 判定示例

- “做一个报销系统”：只读分析，提出接口候选并询问本次接口；禁止先写报销表或测试。
- “增加一个查询本人发票详情的接口”：如果方法、路径、返回字段等仍未确定，先结合项目提出契约，待关键项明确后再改代码。
- “实现 `GET /finance/myinvoice/{invoice_id}`，仅本人可查，返回现有 schema”：先核对现有路由与权限，范围明确即可实现或修正这一个接口及其必要关联代码。
- “一次实现以下两个接口……”：属于明确批量要求，但每个接口仍独立满足分层、注释、进度和验证规则。
